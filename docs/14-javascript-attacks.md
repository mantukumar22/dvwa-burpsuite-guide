# Chapter 14 — JavaScript Attacks (DVWA Module: JavaScript)

## Objective
Defeat a client-side JavaScript "anti-bot" token check that gates a form submission, by reverse-engineering obfuscated JS and replaying the correct token via Burp — illustrating why **client-side logic is never a security boundary**.

## Prerequisites
- Target: `http://localhost/dvwa/vulnerabilities/javascript/`
- Browser DevTools (Sources tab) for reading/de-obfuscating JS
- Burp Repeater

---

## 🟢 LOW

### Source logic
```javascript
// Simple, readable JS: computes a token client-side, submits it as a hidden field
function generateToken() {
    var token = 'success';   // trivially simple in Low
    document.getElementById('token').value = token;
}
```
```php
// Server side
if ($_POST['token'] !== 'success') { die('Invalid token'); }
```

### Burp Suite steps
1. View page source / DevTools to read the trivial token logic.
2. Intercept the form POST in Burp Proxy, or simply craft the request directly in Repeater without ever loading the page or running the JS:
   ```
   POST /dvwa/vulnerabilities/javascript/
   phrase=&token=success
   ```
3. Server accepts it — you never had to execute the client-side JS at all.

### Why it works
The "check" is entirely client-side and its expected value is static/trivial to read or guess — the server blindly trusts whatever token arrives, regardless of whether the legitimate JS logic actually ran in a real browser.

---

## 🟡 MEDIUM

### Source logic
JS is minified/obfuscated (e.g., variable renaming, string splitting) but functionally still computes a **static or simply-derived** token, e.g., a hardcoded string built via basic string concatenation/reversal:
```javascript
var a = 'ss'; var b = 'succe'; document.getElementById('token').value = b + a;
```

### Burp Suite bypass
1. Use DevTools **Sources** tab (or `view-source:`) to manually trace the obfuscated variable assignments — string concatenation, `.reverse()`, `charCodeAt`, etc.
2. Compute the resulting token by hand or with a quick snippet in the browser console:
   ```javascript
   console.log(b + a);  // "success"
   ```
3. Submit that value directly via Burp Repeater, bypassing the JS execution entirely, same as Low.

### Why the bypass works
Obfuscation increases the *effort* to read the logic but doesn't change the fact that the token is computed from **static, client-visible code** — anyone with a browser console or a few minutes of manual de-obfuscation recovers it, and nothing requires the token to have actually been generated by real JS execution.

---

## 🔴 HIGH

### Source logic
Heavier obfuscation, plus **time-based / rotating** derivation — e.g., the token might incorporate a value from the DOM at page-load time or a rotating XOR'd string, making static reading harder but still deterministic and computable from client-visible inputs.

### Burp Suite exercise
1. Set a **JavaScript breakpoint** in DevTools at the point where `token` is assigned, to see its final computed value at runtime for a given page load — the most reliable de-obfuscation technique regardless of complexity.
2. Alternatively, use Burp's **Match and Replace** or a small **Python/JS harness** (e.g., Node.js with the extracted function) to programmatically compute the token exactly as the real JS would, then feed that into an automated Repeater/Intruder request.
3. Confirm the server still accepts a token computed **outside** a real browser context, proving the check remains purely client-derived.

### Why it's still risky
No matter how complex client-side obfuscation becomes, if the **server's only check is "does this token match a value derivable from client-visible code/logic,"** it remains bypassable by anyone willing to reverse-engineer or execute that same logic outside the intended flow (headless browser, manual computation, breakpoint inspection).

---

## ⚪ IMPOSSIBLE

### Source logic
```php
// No trust placed in ANY client-side JS logic for security decisions.
// Server issues a server-side, session-bound, single-use random token (like a CSRF token)
// embedded server-side into the page; client JS is cosmetic/UX only, not a security gate.
$_SESSION['token'] = bin2hex(random_bytes(16));
// ...
if (!hash_equals($_SESSION['token'], $_POST['token'] ?? '')) { die('Invalid token'); }
unset($_SESSION['token']); // single use
```

### Why the attack fails
The security-relevant value is generated and validated **entirely server-side**, using a CSPRNG, bound to the user's session, and single-use. No amount of client-side JavaScript reverse engineering helps, because the correct value was never derivable from client-visible code in the first place — it's a server secret only revealed once, per legitimate page load, to that session.

### Burp Suite exercise
Attempt to compute/predict the token via any client-side analysis — impossible, since it's random server state. Replaying a previously used token also fails (single-use), demonstrating the fix eliminates the entire attack class rather than raising the reverse-engineering bar.

---

## Root Cause Analysis
This module's core lesson: **any security decision made or validated purely in client-side JavaScript is fundamentally untrustworthy**, because the client (browser, DevTools, Burp, curl, custom scripts) is fully under the attacker's control. Obfuscation raises analysis cost but never converts a client-side check into a real security boundary.

## Defensive Takeaways
- Never rely on client-side JS for authentication, authorization, or anti-automation decisions — treat all client-side logic as UX only.
- Any anti-bot/anti-automation or integrity check must be validated with a **server-side, session-bound secret** the client cannot derive or predict.
- Use standard, vetted patterns (CSRF tokens, server-issued nonces, real CAPTCHA APIs) rather than custom "security through obscurity" JS puzzles.
- Assume all client-side code, however obfuscated, will eventually be fully reverse-engineered.
